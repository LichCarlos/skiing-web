# RAG 来源管理真实 HTTP 联调

负责人：Web Admin。范围：已确认的 D-46 / ADM-18 / API-AI-03，以及 D-52 后的 OpenAPI 1.51.1。来源生命周期实现见[读取与命令核对](rag-source-lifecycle.md)，运行入口见[独立管理端 HTTP 联调](admin-authorization-live-http.md)。没有新增业务协议、权限或迁移。

`apps/admin/test/authorization.http-spec.ts` 新增六项顺序场景，现行套件共二十一项。它通过生产 `apiRequest`、`readRagPage`、`readRagSource`、`writeRagCommand` 和恢复控制器访问编译后的 Nest，后端使用全新 PostgreSQL 17 / pgvector 临时库。前端测试不导入后端或数据库代码。

| 场景         | 核对内容                                                                                                                                      |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------------- |
| 列表与详情   | 原始 HTTP 响应及生产解析器的固定元数据投影；排除未支持的来源类型；关键词、状态、类型、人工开关和偏移分页；模型名称稳定排序、1024 维及失败标记 |
| 授权拒绝     | 自定义角色即使拥有三个 RAG grants，仍不能使用仅 system_admin 开放的来源管理；服务端四种读取/写入请求均 403，生产读取器也会在发出请求前拒绝    |
| 重建与空操作 | 重建返回 202、pending 和事件 ID；原有分块不会因受理而视为重建完成；旧版本返回 409；匹配版本的同状态启用不改版本、不写事件或审计               |
| 人工启停     | 停用清空真实 vector(1024) 分块及模型目录；停用期间不能重建；重新启用提交新代次和事件，业务来源本身保持发布状态                                |
| 响应丢失恢复 | 真实命令成功返回后，在客户端请求边界注入错误；记录跨控制器重新创建保留，重复提交被阻止；须成功读取当前目标并显式确认，才能提交后续命令        |
| 并发版本冲突 | 同一 expectedVersion 的两条真实启用请求并发发送，只有一条成功，另一条 409；不重试失败写入                                                     |

后端后置核对最终控制版本 7、索引代次 6、分块数 0，六条控制审计和四条待投递重建 Outbox 对应版本 2/4/5/7。客户端事件 ID 与数据库逐条匹配；失败/不支持的其他来源保持初始版本和状态；原项目知识正文、发布状态与版本保持。拒绝请求 trace 没有成功审计，原账号、商家、字段和会话审计断言继续执行。

首轮新增六项均通过，但旧场景沿用授权变更前的账号快照，触发正确的身份变更拒绝并连带导致四项失败。修正测试的身份恢复步骤为读取当前 `/auth/me`，生产鉴权与业务代码保持。另在类型预检时将不符合本仓 lib 的 findLast 改为复制数组后反转查找。失败日志与最终结果见[本仓验证摘要](../validation/rag-source-http-20261103.json)。

这套验证证明实际 HTTP、事务和数据库效果。Node Cookie jar 只核对 Cookie/CSRF 线协议；不能替代浏览器 Cookie、CORS、React 重挂载或 BFCache 验收。响应丢失是成功提交后的边界故障注入，不是真实网络断线实验。恢复记录仍仅在标签页内存中，不能跨完整刷新或设备，也不能证明历史请求的执行归属。

Kafka 消费者与 Outbox 投递在本套件关闭，pending 事件只证明事务落库。没有调用 Embedding 或对话供应商，没有启动 Next、Expo Web 或 Docker；不计为索引生成、模型回答、浏览器、真机、容器或生产验收。
